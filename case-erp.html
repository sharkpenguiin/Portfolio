Case 01 · B2B ERP

제약 유통 B2B ERP
기획 전 체계를 설계하다

사용자 그룹 5종(병의원·약국·CSO·도매업체·제약사)이 쓰는 18개 화면·기능을 요구 정의부터 개발 핸드오프까지 단독 기획했습니다.
회의마다 갱신되는 요구는 PRD·결정로그·제품 정책으로 관리했고, 반복되는 기획 업무는 커스텀 AI 스킬 10종으로 자동화해 제 업무 시간을 약 40% 줄였습니다.

기간 2026.04 – 2026.06 역할 PM · 단독 기획 산출물 PRD · 기능명세 · 결정로그
18기획 메뉴
5사용자 그룹
20+결정 로그
1인단독 기획
Real artifact · IA 정보구조도 실물 (비식별화)

직접 설계한 ERP 전체 정보구조 — 18개 메뉴 최종본

고객사 ERP 정보구조도

실제 프로젝트 최종본입니다.
고객사명만 비식별화했고 구조는 그대로 — 로그인부터 시스템 설정까지, 이 트리의 각 메뉴가 SCR-ID 단위 PRD와 1:1로 연결됩니다.

문제

Problem

거래처마다 다른 규칙

5개 유형별로 단가·여신·반품 정책이 제각각.
화면 하나에 모든 예외를 담을 수 없었습니다.

회의마다 뒤집히는 요구

확정한 사항이 다음 회의에서 번복. 무엇이 왜 바뀌었는지 추적할 수 없었습니다.

기획자는 한 명

18개 화면·기능을 혼자 설계하며 정합성까지 지켜야 했습니다.

판단

Judgment

화면을 그리기 전에, 순서와 규칙을 담을 그릇을 먼저 설계했습니다.

01

구축 순서를 뒤집었습니다

마스터데이터부터 잡으려던 순서를 정산(EDI·흡수율) → 마스터데이터 → 협력사 포털로 뒤집어 고객사와 확정했습니다. 고객사조차 인지하지 못한 실제 데이터 흐름이 그 반대였기 때문입니다.

마스터를 한 곳에서 통째로 받는 게 아니라, EDI 자료를 먼저 받아 심평원 데이터로 검증한 뒤 마스터로 넣는 구조였습니다.

정산 오류가 곧 억 단위 손실로 이어지는 도메인이라, 이 순서가 먼저여야 뒤가 꼬이지 않습니다.

02

규제를 화면과 필드로 번역했습니다

CSO 신고제·경제적 이익 지출보고·재위탁 통보·CP(공정거래 자율준수)를 화면·필드·검증 규칙으로 정의했습니다. 제약 유통은 법이 곧 요구사항인 도메인입니다.

고객사가 전달한 요건을 그대로 받지 않고 재검토했고, 추가로 확인이 필요한 관련 법령은 직접 찾아 보고했습니다. 규제 미반영으로 인한 재작업은 개발이 아니라 기획 단계에서 막아야 합니다.

03

같은 기능도 누가 보느냐에 따라 달랐습니다

사용자 그룹 5종의 권한·데이터 접근 정책을 정의하고, 프로토타입으로 화면 단위까지 구현해 개발 착수 전에 확정했습니다.

병의원·약국·CSO·도매업체·제약사는 접근 가능한 화면과 데이터 범위가 각각 달랐습니다. 실제로 무엇이 보이고 무엇이 가려지는지 화면으로 확인한 뒤 확정했습니다.

04

예외는 화면이 아니라 제품 정책으로

사용자 그룹별 규칙을 코드에 박지 않고 파라미터 표로 분리했습니다. 새 유형이 생겨도 표에 행만 추가하면 됩니다.

레거시 데이터 2,400만 행(엑셀 기반) 규모를 분석해 마이그레이션 정합성 리스크도 사전 식별했습니다.

05

모든 결정에 근거와 출처를

3개월간 20회 이상의 회의에서 바뀌는 요구를 결정로그로 통제했습니다.

결정·근거·출처·상태 라벨을 남겨, 번복돼도 과거 회의록 재검토 없이 근거를 즉시 소명합니다.

06

화면 단위 PRD 체계 — SCR-ID

화면 1개 = 문서 1섹션, 10섹션 구조. 각 화면에 SCR-ID를 부여해 PRD·기능명세·결정로그가 같은 ID로 연결되도록 설계했습니다.

07

정합성은 사람이 아니라 체크리스트로

18개 화면·기능 간 필드·상태 정합성을 AI 스킬 기반 검증 체크리스트로 통제해 누락을 구조적으로 방지했습니다.

정보구조(IA) 기준으로 구현 범위를 이번 범위와 차기 과제로 분류·합의해 범위 확산도 함께 통제했습니다.

산출물

Output

결정로그·SCR-ID 문서·파라미터 표 샘플 (실제 산출물 기반 재현본 · 고객사·사내 정보 비식별화).

Real artifact · 결정로그 실물 발췌 (비식별화)

메뉴별 결정 로그 — “거래처 · 약국” 섹션 원문

· 약국만(도매 분리), 미분류 거래처 → 백그라운드 사업자 조회로 재분류 〔260408,260506〕

· 도매매출로 자동생성, 코드 3시작 6자리, 상태↔개폐업 분리, 가등록(명칭·사업자·주소) 〔260615,260618〕

· 원내약국 = 도매매출 자동 분류(병원 귀속, 등록 시점엔 모름) 〔260618〕

· 🔵 심평원 사업자번호 조회 가능 시 국세청 대체(요양기관 단독)·폐업일자 〔260618〕

· 연계병원 흡수율 섹션 = 혼선 → 제거(실제 요청은 EDI/도매매출 내역 조회) 〔260618〕

줄 끝 〔날짜〕 = 출처 회의. 🔵 = 현업 확인 필요(미결). 회의록은 시간순 원본으로 두고 결정만 메뉴 키로 누적하는 이중 구조라, 명세 작성 시 과거 회의록 전체를 다시 볼 필요가 없습니다.

Real artifact · PRD 실물 발췌 (비식별화)

약국 관리 PRD — 개념정의 · 화면 목록 원문

용어정의
정식 명칭사업자등록증/요양기관상 법적 약국명(조회·검증 기준)
요양기관번호심평원 부여 식별번호. 직접 수신 불가 재확인 → 확보 방식 미결(크롤링/RPA vs 공공연동, D-9)
원내약국병원 납품 약국. 등록 시점엔 모름 → 도매 매출자료에서 동일 사업자 유입 시 자동 분류
